## 대시보드 원본 데이터 — 자산 인벤토리

`frontend/scripts/build_map_data.py`가 분석 저장소 대시보드에서 데이터를 추출한다(출처 URL + SHA256 기록). **대시보드가 단일 소스이고 우리 파일은 파생물이다** — 원본이 바뀌면 스크립트를 다시 돌린다. 이중 관리가 아니다.

대시보드 `const data` 안에 든 것 전부와, 우리가 쓰는지 여부다.

| 키 | 내용 | 사용 | 용량 |
|---|---|---|---|
| `dongBoundaries` | 82개 행정동 경계 (vuski/admdongkor, MIT) | ✅ A22 | 현재 파일의 대부분 |
| `boundaries` | 5개 자치구 경계 (OSM/Nominatim, **ODbL**) | ✅ A22 | 포함 |
| `dongMetrics` | 동별 `density`·`hhi`·`survival` × 6시점 | ⚠️ **density만** — 나머지 둘은 **이미 파일에 들어 있는데 화면이 안 쓴다** | 포함 |
| **`mapPoints`** | **실제 위경도 + 업종 + 점포 수** (시점당 ~2,300점, 10업종, count 합 80,704) | ❌ 미사용 → **A25** | 1시점 203KB / 전체 1.2MB |
| **`dongs`** | 동별 **절대 업소 수** 시계열 | ❌ 미사용 → **A23** | 10KB |
| **`dongTurnover`** | 동별 폐업(`left`)·개업(`entered`) 5구간 | ❌ 미사용 → **A23·A26** | 6KB |
| `combinations` | 자치구 × 업종 (50조합) | ❌ 미사용 — 구 단위 5개뿐이라 지도 가치 낮음 | 7KB |
| `categories`·`city` | 시 전체 업종·총계 시계열 | ❌ 지도용 아님 | — |

현재 `daejeon-map.json`은 **365KB**다.

- `dongs` + `dongTurnover` = **+16KB**. 사실상 공짜.
- `mapPoints` 최신 1시점 = **+203KB** (좌표 4자리로 줄여도 198KB, 효과 미미).
- `mapPoints` 전 시점 = **+1.2MB** → 합 1.5MB. **`roadmap.md` 리스크 표에 "대시보드 1.8MB 단일 파일"이 이미 올라 있다. 같은 실수를 반복하지 않는다.**

### 임베드 패널 캐시

패널은 `?only=<섹션>` 쿼리로 같은 1.78MB 파일을 부른다. 응답 헤더가 `Cache-Control: max-age=600`이라 **10분 안에 다시 열면 네트워크 요청이 없다.** 다만 브라우저 캐시 키는 쿼리를 포함하므로 **서로 다른 섹션은 각각 첫 로드 비용을 낸다.** 8개를 다 보면 최악 14MB, 5개면 8.9MB다. → A27이 패널 수를 5개로 줄이는 근거.

## 주의

- **B2 재실행 안전성이 수용 기준이다.** 대량 적재는 중간 실패가 잦으므로 upsert가 아니면 중복이 쌓인다.
- **B2 완료 후 D3(시드 리셋)의 성격이 바뀐다** — 복구 대상이 커져 배치 삭제·재적재가 필요하다. → [`C-reliability-ops.md`](C-reliability-ops.md)
- **B2 완료 후 C5(요약 캐시)가 사실상 필수가 된다** — 매 채팅마다 전량 집계는 비현실적이다.
- 수치를 바꾸면 `frontend/js/topics-data.js`와 `backend/app/seed/insights.md`가 **같은 출처를 써야 한다.** 한쪽만 고치지 않는다.


## 점 데이터의 한계 — 행정동 업종 구성은 만들 수 없다

A26에서 *"이 동에 무슨 업종이 많은가"* 를 붙이려고 `mapPoints`(2,321점)를 행정동 경계에 떨어뜨려 봤다. **못 쓴다.**

점을 경계에 넣는 것 자체는 완벽했다 — 광선 투사로 80,704개 전부가 82개 동 중 하나에 들어갔고 **경계 밖 0개**였다. 문제는 그다음이다. 동별 합계를 `dongs`의 등록 업소 수와 맞춰 보니 어긋난다.

| 오차 | 동 수 |
|---|---|
| 5% 이내 | 14 / 82 |
| 10% 이내 | 27 / 82 |
| 30% 이내 | 52 / 82 |

| 최악 사례 | 점 기준 | 등록 | 오차 |
|---|---|---|---|
| 대덕구 법1동 | 555 | 174 | **219%** |
| 서구 괴정동 | 3,596 | 2,041 | 76% |
| 서구 탄방동 | 902 | 2,857 | 68% |

**원인은 점이 개별 점포가 아니기 때문이다.** 점 2,321개가 업소 80,704개를 나타내니 점 하나가 평균 35개 묶음이다. 격자 집계된 좌표라 셀이 경계를 걸치면 통째로 한쪽 동에 들어간다. 작은 동일수록 심하다.

교차검증도 같은 말을 한다 — 점으로 계산한 HHI와 `dongMetrics.hhi`의 평균 오차가 0.036, 최대 0.31(용두동 0.49 vs 0.183)이다.

**결론**: `mapPoints`는 **분포를 눈으로 보는 용도(A25 점 레이어)** 로만 쓴다. 행정동 단위로 세는 데는 쓰지 않는다. 대시보드에 행정동 × 업종 집계는 없다 — `combinations`는 자치구 × 업종(5×10)이라 동 단위 질문에 답하지 못한다.

A26은 그래서 업종 구성 없이 2축만으로 간다. 대신 업종이 고르게 섞였는지는 `hhi` 지표가 이미 정확하게 답한다.

## B5(RAG)를 지금 하지 않는 이유 — 2026-09-09 실측

스펙은 *"리포트가 커지면"* 전체 주입 대신 관련 청크만 넣자고 했다. **그 조건이 아직 아니고, 지금 바꾸면 오히려 손해다.**

| | |
|---|---|
| 리포트 전체 | **1,810자 ≈ 996토큰** (8개 섹션, 평균 226자) |
| 고정 프리픽스 | **2,460자** — 전부 캐시 대상 |

RAG로 바꾸면 리포트가 질문마다 달라지므로 프리픽스가 **2,460자 → 650자**로 줄어든다. OpenAI 자동 캐싱의 1,024토큰(약 1,860자) 임계 미달이라 **캐시 적중이 0이 된다.**

| | |
|---|---|
| 절약 | 섹션 1~2개만 넣으면 입력 약 **696토큰** 감소 |
| 손해 | 캐시 적중 1,024토큰의 50% 할인 소멸 ≈ **512토큰**어치 |
| 추가 비용 | 질문마다 임베딩 API 호출 1회 (지연 + 요금) |
| 추가 위험 | 사용자가 화면에 없는 주제를 물었을 때 **해당 섹션을 놓칠 수 있다** |

순이득이 약 180토큰인데 그 대가로 지연·요금·누락 위험이 붙는다. **안 한다.**

### 언제 다시 보나

리포트가 **약 4,000자(2,200토큰)를 넘을 때.** 그쯤이면 관련 섹션만 넣어도 프리픽스가 1,860자를 유지할 수 있어 캐시를 잃지 않는다. B2가 업종 × 행정동으로 커지거나 시점이 늘면 그 선에 닿는다.
