# G. 온톨로지 — 질문이 화면을 세팅한다

> **상위**: [스펙 인덱스](README.md) · [문서 허브](../PORTFOLIO_SPEC.md) · **작성**: 2026-09-11
> 범례: **P0/P1/P2** 우선순위 · **S** ≤0.5일 / **M** 1~2일 / **L** 3일+

**참조** — 화면 컨텍스트 화이트리스트는 이미 있다(`backend/app/models.py`의 `CONTEXT_KEYS`). 지명 사전도 이미 있다(`frontend/js/map.js`의 `initRegionSearch`). 이 그룹은 **그 둘을 반대 방향으로 잇는다.**

---

## 왜

지금은 **화면 → 채팅** 한 방향이다. 고른 주제·지역·페르소나가 프롬프트에 실린다.

반대는 비어 있다. *"용문동은 가게가 얼마나 자주 바뀌어?"* 라고 물으면 **AI는 말로 답하고 지도는 딴 데를 보고 있다.** 눈으로 확인하려면 지표 셀렉트를 열어 `점포 교체율`을 고르고, 검색창에 `용문동`을 치고, 검색을 누른다 — **4동작**이고, 그마저 *교체율이라는 지표가 있다는 걸 알아야* 가능하다.

그리고 **콜드스타트 43초가 통째로 버려진다.** 그동안 화면이 이미 답을 보여주고 있으면 체감이 완전히 달라진다.

---

## 이 그룹의 범위

**하는 것** — 질문에서 지표·지역·시점·무대를 알아내 화면을 맞춘다. **못 답하는 질문이면 화면을 바꾸지 않는다.**

**무대는 둘이다** — 지도(행정동 코로플레스 7지표)와 대시보드 5탭(임베드). 둘은 축도 입도도 다르고, **같은 라벨이 다른 개념을 가리키는 곳도 있다**(`점포 교체율`). 사전은 둘 다 알아야 한다.

**안 하는 것**
- OWL·추론기·트리플스토어. 이 규모에서 과하다. **통제 어휘 + 제약표**까지다.
- 다만 **JSON-LD `@context`는 얹는다** — 런타임 비용이 0이라 "안 하는 것"에 둘 이유가 없다. 근거와 정확한 형태는 [부록 A](#부록-a-json-ld--왜-이것만-얹는가).
- 화면 세팅에 LLM을 부르지 않는다(G3 근거 참조).
- 질문을 대신 보내지 않는다. 화면만 맞추고 답은 사용자의 질문 그대로 받는다.
- 사용자가 맞춰 둔 것을 말하지 않은 부분까지 바꾸지 않는다.

| 입도 안 맞는 질문 | 엉뚱한 탭을 열고 답한 척 | **무대를 안 바꾸고 이유를 말함**(G5) |

**커버리지는 60~70%로 본다.** *"작년보다 나아진 동네"* 같은 질문은 사전으로 안 잡힌다.

**안 잡히면 지금과 똑같다.** 화면이 안 바뀔 뿐 후퇴가 없다 — 이것이 LLM에 시키는 것과의 결정적 차이다. LLM은 **틀리게** 바꿀 수 있다.

> **이건 이해가 아니라 패턴 매칭이다.** 그래서 G4의 *"말한 것만 바꾼다"* 와 *"되돌리기"* 가 선택이 아니라 전제다.

## 순서

**G2 → G1 → G3 → G4 → G5 → G7 → (G6)**

거절부터 만든다. G2만 있어도 *"매출 질문에 화면이 움직이지 않는다"* 는 성립하고, 그것만으로 이 서비스의 주장이 화면에서 증명된다.

**G5가 뒤에서 앞으로 올라왔다.** 처음에는 "비교 질문을 적절한 탭으로 보낸다"는 편의 기능으로 봤는데, 다시 보니 **입도가 안 맞는 무대로 보내는 것이 G2와 같은 종류의 실패**였다 — 답할 수 없는 것을 답한 척하는 것. 편의가 아니라 정확성 항목이다.

G6는 마지막이다. 제약 위반은 드물고, 어긋나도 화면이 이상해질 뿐 틀린 답을 주지는 않는다.

## 부록 A. JSON-LD — 왜 이것만 얹는가

### 한 줄

**JSON-LD는 그냥 JSON이다.** `@context` 키 하나가 더 있고, 그 키가 *"이 파일의 `label`은 schema.org의 `name`을 뜻한다"* 라고 적어 둔다. 그 선언 덕분에 같은 파일이 **유효한 RDF**가 된다 — 파일을 바꾸지 않고, 파서를 바꾸지 않고.

```js
// @context가 있든 없든 이 줄은 똑같이 돈다
const dict = await (await fetch("/data/ontology.json")).json();
dict.metrics.turnover.aliases;   // ["교체율", "망하", ...]
```

`resolveIntent()`는 `@context`를 **한 번도 읽지 않는다.** 런타임 비용이 0인 이유가 이것이고, "안 하는 것"에서 이것만 빼낸 이유도 이것이다.

### 키워드는 셋이면 된다

| 키워드 | 뜻 | 우리 쓰임 |
|---|---|---|
| `@context` | 지역 키 → 전역 어휘 매핑 | 파일 맨 위 한 블록 |
| `@id` | 이 노드의 이름(식별자) | `#turnover`, `#dong-30170550` |
| `@type` | 이 노드가 무엇인가 | `PropertyValue`, `AdministrativeArea` |

`@graph`(노드 목록), `@language`(문자열 언어) 정도가 더 있고, 나머지는 우리 규모에서 안 쓴다.

### 우리 파일에 얹으면

```json
{
  "@context": {
    "@vocab": "https://schema.org/",
    "@language": "ko",
    "label":   "name",
    "aliases": "alternateName",
    "unit":    "unitText",
    "metrics": "variableMeasured",

    "answers": null,
    "cannot":  null,
    "periods": null,
    "grain":   null,
    "stages":  null
  },

  "@type": "Dataset",
  "name": "대전 상권 온톨로지 사전",

  "metrics": [
    {
      "@id": "#turnover",
      "@type": "PropertyValue",
      "label": "점포 교체율",
      "unit": "%",
      "aliases": ["교체율", "망하", "폐업", "자주 바뀌", "버티", "오래 가"],
      "periods": "all",
      "grain": "dong",
      "answers": "한 동네에서 가게가 얼마나 자주 바뀌는가",
      "cannot": ["매출", "유동인구", "특정 점포의 생존 여부"]
    }
  ]
}
```

**`null`이 이 블록에서 제일 중요한 줄이다.** JSON-LD에서 용어를 `null`로 두면 *"이 키는 RDF가 아니다"* 라는 **명시적 선언**이 되어 확장 단계에서 빠진다.

`answers`·`cannot`·`grain`은 **이 프로젝트에서만 뜻이 있는 말**이다. 여기에 그럴듯한 IRI를 지어 붙이면(`https://example.com/ns#answers`) 열어도 아무것도 없는 주소가 생기고, 그건 **없느니만 못하다** — 의미가 있는 척하는 장식이다. `null`은 "표준 어휘로는 이걸 못 적는다"를 정직하게 적는 방법이다.

> **규칙: 이미 있는 어휘를 쓰거나, 아니면 `@context`에 넣지 않는다.** IRI를 새로 만드는 순간 그 주소를 유지할 책임이 생긴다.

### 지명에서 실제로 값을 한다

경계 데이터의 용문동 하나가 **식별자를 이미 셋** 들고 있다:

```json
{ "dong_code": "30170550", "source_adm_cd": "25030560", "source_adm_cd2": "3017055000" }
```

같은 동네에 코드 체계가 셋이라는 뜻이고, 이걸 구조 없이 두면 *"30170550이 뭐였더라"* 를 매번 코드에서 되짚어야 한다. JSON-LD에는 정확히 이걸 위한 관용구가 있다:

```json
{
  "@id": "#dong-30170550",
  "@type": "AdministrativeArea",
  "name": "용문동",
  "containedInPlace": { "@id": "#gu-seogu", "name": "서구" },
  "identifier": [
    { "@type": "PropertyValue", "propertyID": "dong_code",      "value": "30170550" },
    { "@type": "PropertyValue", "propertyID": "source_adm_cd",  "value": "25030560" }
  ]
}
```

이건 온톨로지 취향의 문제가 아니라 **이미 있는 혼란에 이름을 붙이는 것**이다.

### 얻는 것 셋

**① 나중에 트리플스토어가 필요해져도 이사 비용이 없다.** RDF 툴은 전부 JSON-LD를 직접 읽는다. 지금 0의 비용으로 선택지를 사 두고, 안 쓰면 안 쓰는 것이다.

**② `index.html`의 `Dataset` 블록 — 이건 진짜 쓰인다.** Google Dataset Search가 데이터셋을 수집하는 방법이 문자 그대로 이것이다.

```html
<script type="application/ld+json">
{
  "@context": "https://schema.org/",
  "@type": "Dataset",
  "name": "대전 행정동 상권 지표 (82개 동, 6시점)",
  "description": "행정동별 공급 밀도·점포 교체율·잔존율·업종 집중도. 매출과 유동인구는 포함하지 않는다.",
  "spatialCoverage": { "@type": "Place", "name": "대전광역시" },
  "temporalCoverage": "2023-06/2025-12",
  "license": "https://opendatacommons.org/licenses/odbl/",
  "creator": { "@type": "Person", "name": "..." }
}
</script>
```

`description`에 **한계를 적는 것**을 눈여겨볼 것 — G2가 화면에서 하는 말을 메타데이터에서도 한다. 공모전 심사자가 열어 보는 첫 화면에서 이 블록은 "데이터 출처와 한계를 아는 사람"이라는 신호다.

⚠️ CSP: 인라인 `<script>`다. `application/ld+json`은 **실행되지 않는 데이터 블록**이라 `script-src`가 막지 않지만, 넣은 뒤 콘솔에서 실제로 확인한다 — 예전에 테마 인라인 스크립트로 한 번 데었다.

**③ `sameAs`로 바깥과 잇는다.** 업종 분류 같은 것을 나중에 표준 코드에 붙일 자리가 생긴다. 지금은 안 한다.

### 못 하는 것 — 여기가 선이다

`@context`는 **뜻을 적을 뿐 검사하지 않는다.**

- 단일 시점 지표에 `periods: "all"` 을 잘못 적어도 **아무도 안 잡는다** → 그건 G6의 제약표와 G7의 CI가 한다
- `@context`만으로는 *"고밀도동"* 같은 새 사실이 안 나온다 → 그게 추론기이고, 우리는 `value >= 100` 비교 한 줄이라 필요 없다
- 질의(SPARQL)도 안 된다 → `resolveIntent()`가 하는 일이다

**즉 JSON-LD는 "표현"만 준다. 검증·추론·질의는 여전히 우리 코드와 CI가 한다.** 그래서 공짜고, 그래서 이것만 얹는다.

### 공수

`@context` 블록 + `Dataset` 블록 = **S 이하**, G1에 딸려 간다. 별도 항목으로 세우지 않는다.
