# 에이전트 역할 분해

> **상위**: [문서 허브](PORTFOLIO_SPEC.md) · **갱신**: 2026-09-08
> 남은 스펙 26건을 **6개 역할 + 조율자**로 나눈다. 나누는 기준은 기술 스택이 아니라 **파일 소유권**이다 — 두 에이전트가 같은 파일을 고치면 병합 충돌이 나고, 충돌 해결에 드는 비용이 병렬화 이득을 넘는다.

---

## 2. 경계 충돌 — 미리 정해둘 것

병렬 작업에서 실제로 터질 지점은 네 곳이다.

### ① `frontend/index.html` — R1과 R2가 함께 만진다

| 구역 | 소유 |
|---|---|
| `<head>` (폰트 로드·메타·`<title>`) | **R2** |
| `<body>` 구조·새 요소 추가 | **R1** |

R2의 A16(웹폰트)·A20(타이틀)은 `<head>`만, R1의 A9(목적 칩)·A12 자리 확보는 `<body>`만 건드린다. 같은 파일이지만 **겹치는 줄이 없다.**

### ② A12(기준 배지) — R1과 R2가 나눠 갖는다

- **R1**: 배지를 넣을 **위치**와 마크업 (주제 버튼 위)
- **R2**: `--caution` 톤·타이포·간격

**순서**: R1이 마크업을 먼저 넣고(회색이어도 무방), R2가 A15에서 톤을 입힌다.

### ③ A14(주제 리포트) — R1과 R3가 나눠 갖는다

- **R3**: 4블록(요약/핵심 수치/해석/한계) 구조를 강제하는 **시스템 프롬프트**
- **R1**: CTA 버튼 · 응답 렌더

**접점**: 리포트 요청을 별도 엔드포인트로 뺄지, `context`에 플래그를 얹을지. **R3가 먼저 정하고 R1에 알린다.**

### ④ A21(대기 상태) — R1과 R5가 나눠 갖는다

- **R1**: 경과 시간 타이머 + 단계적 문구 갱신
- **R5**: F3의 에러 3종 분기 유지 및 **문구 정확성 수정**

**주의**: 현재 `cold` 문구가 "다시 시도해 주세요"인데 실제로는 자동 완료된다. **두 역할이 같은 문구를 서로 다르게 고치면 안 된다.** 문구 소유권은 **R5**, 타이머 동작은 R1.

## 3. 순서 제약 — 어길 수 없는 것

```
R2:A15(토큰 도입)  ──▶  R5:F1(색 대비 검증)
   팔레트가 바뀌는데 먼저 검증하면 두 번 일한다

R4:B2(전량 적재)  ──▶  R3:C5(요약 캐시)  ──▶  R3:D3(시드 리셋)
   전량 데이터가 캐시와 리셋의 성격을 바꾼다

R2:A15  ──▶  R1의 새 CSS
   A15 전에 R1이 색을 하드코딩하면 A15가 그걸 다시 걷어내야 한다
   → A15 전이라면 R1은 기존 클래스만 재사용하고 새 색을 만들지 않는다

decisions.md ⑥(서비스 이름 확정)  ──▶  R2:A20
   미결이면 A20을 시작할 수 없다 (사용자 결정 필요)

R3:B3(요약 필터)  ──▶  R1의 필터 연동
   API가 없으면 프론트가 붙일 데가 없다
```

## 4. 병렬 실행 계획

### Wave 1 — Phase 1-b (지금)

**4개 역할이 동시에 돌 수 있다.**

| 역할 | 작업 | 비고 |
|---|---|---|
| **R1** | A9 → A10 → A11 → A14(UI) → A21(타이머) → A13 | 가장 무겁다. A9·A10이 최소선 |
| **R2** | A16(결함) → A12(톤) | A16은 독립적이라 즉시 시작 가능 |
| **R3** | A14(프롬프트) | R1보다 **먼저** 끝내야 R1이 붙일 수 있다 |
| **R5** | A21 문구 수정 (F3) | 소규모 |
| **R6** | E1(구성도) → E5(README) | 완전 독립 |

**충돌 없음** — R1(js) · R2(css) · R3(python) · R6(md)는 파일이 겹치지 않는다.

### Wave 2 — Phase 2

| 역할 | 작업 |
|---|---|
| **R2** | A15 → A17 → A18 → A19 (A20은 ⑥ 확정 후) |
| **R3** | A4(스트리밍) → C4 → C5 |
| **R5** | C1(pytest) → C2(CI) → C6 |

**주의**: R2의 A15가 `style.css`를 대대적으로 바꾸므로, 이 기간 R1은 CSS를 건드리지 않는다. R3의 A4(스트리밍)는 `chat.js`도 바꿔야 해서 **R1과 접점이 생긴다** — Wave 2에서 R1을 쉬게 하거나, `chat.js` 소유권을 한시적으로 R3에 넘긴다.

### Wave 3 — Phase 3

| 역할 | 작업 |
|---|---|
| **R4** | B2(L+, 가장 김) → B1 |
| **R3** | B3 → C3 (B2 완료 후) |
| **R5** | F1(A15 완료 후) → F2 → C7 |
| **R6** | E2(ADR) → E3(데모) → E4(회고) |

**R4의 B2가 임계 경로다.** 3일+ 걸리고 뒤에 C5·D3·B3가 매달려 있다. **Wave 2와 겹쳐서 먼저 시작하는 것이 낫다.**

## 5. 역할별 작업 규칙

모든 역할 공통.

1. **소유하지 않은 파일을 고치지 않는다.** 필요하면 소유 역할에 요청한다.
2. **스펙 ID를 커밋 메시지에 넣는다** — `feat: A9 목적 칩을 추가한다`. 폐기 번호(A3a·A5·D1·D2)는 재사용 금지.
3. **진행 상태는 [`roadmap.md`](roadmap.md)에만 쓴다.** 스펙 파일에 상태를 적지 않는다. 갱신은 R0 또는 작업 완료 시 본인.
4. **[`decisions.md`](decisions.md)의 결정 완료 항목을 재논의하지 않는다.** 뒤집을 근거가 생기면 결정을 새로 추가한다.
5. **수용 기준을 만족했는지 스스로 확인하고 보고한다.** 미달이면 미달이라고 쓴다.
6. **문서를 고치면 [`CHANGELOG.md`](CHANGELOG.md)에 한 줄 남긴다.**
7. **비밀 정보 금지** — `.env` · `firebase-service-account.json`은 커밋하지 않고 값을 노출하지 않는다.
8. **사용자에게 보이는 텍스트는 한국어로 쓴다.**

## 6. 최소 구성

역할을 6개 다 띄울 필요는 없다. 규모별 권장.

| 규모 | 구성 | 비고 |
|---|---|---|
| **1인** | 순차 진행 | Wave 1 순서(R3 프롬프트 → R1 UI → R2 톤)만 지키면 된다 |
| **3역할** | R1(프론트 전체) · R3(백엔드+데이터) · R6(문서) | R2를 R1에, R5를 R3에 흡수. **가장 실용적** |
| **6역할** | 위 정의대로 | Phase 2·3처럼 작업량이 넓게 퍼질 때만 |

> **과분할 주의**: 스펙 하나가 S(≤0.5일)인데 역할을 나누면, 인계 비용이 작업 시간보다 커진다. **M 이상 항목이 2개 이상 쌓인 역할만 분리할 가치가 있다.**
