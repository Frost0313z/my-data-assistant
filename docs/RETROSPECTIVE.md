## 이 프로젝트가 실제로 어려웠던 지점

### 1. 데이터가 답할 수 없는 것을 답하는 척하지 않기

이 데이터에는 **매출과 유동인구가 없다.** 점포 수와 위치뿐이다. 그런데 사용자가 묻고 싶은 것은 "여기 창업해도 될까요"다.

가장 많은 시간을 쓴 것이 기능이 아니라 **이 간극을 어떻게 다룰지**였다.

- 증감에 초록/빨강을 쓰지 않는다 — 증가가 좋은 일인지 우리는 모른다. 실제 반례가 있다: 목동은 잔존율 최저(73.7%)인데 **+5.3% 늘었고**, 대흥동은 밀도 2위인데 **+0.4%로 멈췄다.**
- 지역을 점수로 줄 세우지 않는다 — 밀도만 9.4~596.6으로 퍼져 있어 가중합은 사실상 밀도 하나짜리가 된다.
- A26 지역 유형의 이름을 전부 묘사로 썼다(`촘촘하고 자주 바뀌는 곳`). `유망`·`침체`는 우리가 할 수 없는 판단이다.

**그런데도 새어 나갔다.** A26을 만들고 "이 유형은 좋은 거야?"라고 물었더니 AI가 *"좋은 지역 유형이라고 할 수 있습니다"* 라고 답했다. 유형은 **화면이 만든 구분이라 AI가 그 존재를 몰랐고**, 아는 다른 지표(LQ 3.48)로 갈아탄 것이다. 화면에서 아무리 조심해도 프롬프트가 모르면 소용없다는 것을 그때 배웠다.

### 2. "보인다"와 "읽힌다"는 다르다

대시보드에는 정보가 다 있었다. 부족한 것은 데이터가 아니라 **표현**이었다.

임베드를 세로로 쌓았더니 답답했고, 하단 탭으로 무대를 바꾸게 하니 풀렸다. 목적 칩을 만들었더니 "칩이 UX상 인지되기 어렵다"는 지적을 받아 카드로 승격했다. 이런 것들은 스펙을 아무리 잘 써도 화면에 띄워 보기 전엔 몰랐다.

### 3. 무료 티어의 제약이 설계를 바꾼다

| 제약 | 설계에 남긴 것 |
|---|---|
| Render 15분 뒤 절전, 깨는 데 **42.7초**(실측) | A21 단계적 대기 문구, C6 10분 예열 |
| Firestore에 `GROUP BY`가 없다 | 요약을 파이썬에서 계산 → C5 캐시가 필수가 됨 |
| Firestore 배열의 부분 갱신이 안 된다 | `append_turn` 경합 → 트랜잭션 |
| 인스턴스가 하나 | 남용 방어를 인메모리로. 여러 개로 늘리면 상한이 그만큼 느슨해진다 |

## 배운 것

### 스크린샷은 "가려진 것"을 못 보여준다

브라우저 검증에서 가장 큰 결함은 **화면이 멀쩡해 보이는 것**이었다. 하단 탭은 잘 보였고, 그 아래 범례·선택 결과·질문 버튼이 접힘선 밖으로 밀려 있었다. `getBoundingClientRect`로 재고 나서야 보였다 — 질문 버튼이 1066px, 접힘선이 1000px.

그 뒤로는 눈으로 보는 대신 **좌표와 CSSOM을 전수 조회**했다. 색 대비도 그렇게 쟀다(위반 0건).

### 응답이 멀쩡한 고장이 제일 위험하다

이번에 만든 것 중 절반은 **조용한 고장을 시끄럽게 만드는 장치**다.

- 프롬프트 캐시 프리픽스가 깨지면 응답은 똑같고 **비용만 두 배**가 된다 → 테스트가 프리픽스 길이를 지키고, 로그가 `cached_tokens`를 남긴다.
- 답변이 상한에 걸려 잘리면 화면에서는 "문장이 좀 어색한" 것으로만 보인다 → 로그에 `truncated`.
- 설정이 안 먹으면 알 방법이 없었다 → 시작 로그가 실효값을 남긴다. **실제로 `CHAT_MAX_TOKENS`가 `.env`에 덮여 답변이 계속 잘리고 있었는데, 코드 기본값만 고치고 해결됐다고 착각했다.**
- 리포트가 낡으면 AI가 틀린 근거를 댄다 → CI가 리포트의 수치를 데이터와 대조한다.

### 테스트가 잡은 것은 대부분 "테스트 밖"의 문제였다

pytest 스위트를 쓰면서 잡은 것들:

- 프로세스 전역 상태가 테스트 사이로 샜다(요약 캐시, 남용 카운터). 프로덕션에서는 맞는 설계라 코드 문제가 아니었지만, **한 인스턴스 안에서 상태가 얼마나 오래 사는지**를 그때 정확히 알게 됐다.
- 대역(fake) 자체에 버그가 있었다. 스냅샷이 데이터를 참조로 들고 있어서, 정작 잡아야 할 경합이 재현되지 않고 있었다. **테스트가 통과하는데 아무것도 검증하지 못하는 상태**였다.
- 그래서 회귀 테스트를 쓴 뒤 **옛 코드로 되돌려 실제로 실패하는지** 확인했다. 통과하는 테스트보다 실패시킬 수 있는 테스트가 중요하다.

### 검사 방식이 틀리면 멀쩡한 것을 틀렸다고 말한다

B1에서 "데이터의 최저·최고가 리포트에 있는가"로 쟀더니 리포트가 틀렸다고 나왔다. 그런데 리포트의 "최저권: 목동 73.7%"는 **최소값 주장이 아니라 예시**였다. 검사를 "리포트가 인용한 (행정동, 숫자)가 데이터에 있는가"로 바꾸니 진짜 문제가 드러났다 — 한 문장 안에서 **두 달의 값이 섞여 있었다.**

## 마지막 하루 — 만드는 방식에서 배운 것 (2026-09-10)

앞의 내용은 **제품**에서 배운 것이다. 마지막 날에는 **일하는 방식**에서 나왔다.

### 규모

| | |
|---|---|
| 기간 | 2026-09-08 ~ 09-10 (3일) |
| 커밋 | **135개** (머지 21) · feat 56 · docs 37 · fix 13 |
| 코드 | 6,652줄 / 문서 약 3,800줄 (34개 파일) |
| 스펙 항목 | 51개 · roadmap 완료 63행 · 보류 4건 |

**문서가 코드의 약 58%다.** 값을 한 쪽과 아닌 쪽이 갈린다.

### 값을 한 문서 — 스펙이 실제로 미래를 맞혔다

[`A32`](specs/A-product-ux.md)에 *"그냥 뒤집으면 깨지는 것 다섯 가지"* 를 미리 적었는데 **다섯 개 전부 실제로 깨졌다.** 구현 중에 여섯 번째(MapLibre `background` 레이어)가 나왔다. 미리 쓴 다섯이 없었으면 여섯을 전부 현장에서 만났을 것이다.

`안 한다`에 **되살릴 조건**을 붙인 것도 같은 값이다 — B5는 *"리포트가 4,000자를 넘으면"*, C7은 *"백엔드 로그로 설명 안 되는 화면 오류 신고가 들어오면"*. 그냥 "안 함"이면 반년 뒤에 이유를 아무도 모른다.

### 비용은 아무도 재지 않는 비기능 요구사항이었다

**하루 Firestore 읽기 한도(5만)를 태워 서비스가 멈췄다.** 원인은 버그가 아니라 구조다 — `display:none`인 사이드 패널을 위해 부팅마다 492건을 통째로 읽었고, 방문자 한 명당 약 500 reads라 100명이면 하루치가 끝난다.

**어떤 테스트도 이걸 잡을 수 없었다.** 기능은 정상이고 응답도 200이었다. 위의 *"응답이 멀쩡한 고장"* 과 같은 종류인데, 그때는 **비용 축을 빠뜨렸다.**

### 재보지 않은 제약을 스펙에 사실처럼 적었다

결정을 **8번** 뒤집었고, 대부분 이 이유였다.

| 적었던 것 | 실제 |
|---|---|
| "헤더에 넷째 버튼은 안 들어간다" | 라벨을 두 자로 줄이니 **49px, 넘침 0** |
| "브랜치 보호는 대시보드 작업이라 코드로 못 넣는다" | `gh api` **한 줄** |

두 번째는 검증 없이 여러 번 옮겨 적힌 메모였다. **제약은 측정값일 때만 제약이다.**

### 규칙 하나가 같은 종류의 두 번째 실수를 못 막았다

캐시된 옛 스크립트를 보고 *"코드가 안 먹는다"* 고 오진 → `ignoreCache로 새로고침한다`를 규칙으로 남겼다. 그런데 **같은 날 또**, 열려 있던 탭의 잔여 상태를 보고 *"부팅에서 API를 3건 부른다"* 고 했다.

규칙이 **사례 수준**이라 좁았다. `캐시`만 다루고 `상태`는 안 다뤘다. 원인 수준(*"브라우저에 남은 상태를 의심한다"*)으로 썼으면 둘 다 막혔다.

### 병렬 구현은 실패했고 차가운 두 번째 독자는 성공했다

파일 소유권으로 나눈 병렬 작업은 무너졌다 — `style.css` 최근 커밋 7개가 전부 조율자 것이라 경계가 문서에만 남았다. 1인 규모에서 충돌 관리 비용이 병렬화 이득을 넘는다.

그런데 **11개 머지 뒤처진 낡은 코드를 보고도 진짜 결함 3건을 찾았다.** 그중 하나는 조율자가 쓴 코드이고 조율자가 못 본 것이다. → 역할을 읽기 전용 검토자로 재정의([`roles/README.md`](roles/README.md)).

### 정확성 검증을 단순성 검토로 착각했다

마지막 항목([`A33`](specs/A-product-ux.md))을 구현하고 *"검증 전부 통과"* 라고 보고한 직후, 단순성 리뷰가 **같은 41줄에서 15줄어치 과설계**를 찾았다 — 걸리지 않는 `flex: 0 0 auto` 두 개, 래퍼 `div` 없이 기존 선언 두 개(`flex-end` + 제목 `margin-right: auto`)만 고치면 되는 것. 고쳐서 측정까지 마쳤다(+35 → +19줄, 화면 결과 동일).

**그런데 올리지 못했다.** 머지하려는 사이 `main`에 브랜드 로고와 네이비 헤더가 들어왔고, 그 작업이 **`.header-actions`와 `.header-divider`에 규칙 다섯 개를 새로 얹은 뒤였다.** 래퍼는 이제 값을 한다. 걷어내려면 남의 새 스타일을 내가 화면으로 본 적도 없는 상태에서 다시 써야 한다 — **리뷰는 그때 옳았고 지금은 옳지 않다.** 되돌렸다.

두 가지를 같이 배웠다. **검증 통과는 완료가 아니다.** 그리고 **리뷰 결과에도 유통기한이 있다** — 근거가 "이 래퍼는 아무것도 안 한다"였는데, 하루 만에 그 전제가 사라졌다. 지적을 받은 즉시 올렸으면 적용됐을 것이고, 하루 늦었으면 그냥 틀린 지적이 된다.

## 다음에 한다면

1. **화면을 먼저 띄우고 스펙을 쓴다.** 목적 칩 → 카드, 세로 스택 → 무대 전환처럼 화면에서만 드러나는 것이 많았다.
2. **로그를 처음부터 넣는다.** C4를 나중에 넣었는데, 그 전에 겪은 문제(설정이 안 먹음, 답변이 잘림, 캐시 미적중) 대부분이 로그 한 줄이면 끝났을 것이다.
3. **AI가 모르는 것을 화면에서 만들지 않는다.** 만들 거라면 그 정의를 프롬프트에 같이 보낸다(A26에서 배운 것).
4. **첫날에 비용 예산을 적는다** — *"방문자 1명당 Firestore 읽기 N건 이하"* 를 기능 요구사항과 같은 자리에.
5. **"불가능"은 측정값과 함께만 적는다** — 안 재봤으면 `미확인`이라고 쓴다. 뒤집힌 8건 중 최소 3건이 이걸로 막혔다.
6. **규칙은 사례가 아니라 원인 수준에서 쓴다** — 같은 종류의 오진을 두 번 하고 나서 알았다.
7. **구현 직후 단순성 패스를 붙인다** — 검증 통과 뒤에 한 번 더 줄인다.
