# ADR 0003 — 파인튜닝·RAG 대신 컨텍스트 주입을 쓴다

**상태** 유효 · **날짜** 2026-09 (사후 기록)

## 맥락

AI가 대전 상권 데이터를 근거로 답해야 한다. 근거가 되는 것은 **사전 분석 리포트**(`insights.md`, 1.8KB)와 **실시간 요약**(현재 저장된 레코드), 그리고 **사용자가 화면에서 고른 것**(주제·행정동·목적)이다.

## 결정

**시스템 프롬프트에 통째로 넣는다.** 블록은 넷이다 — `[사전 분석 리포트]` · `규칙` · `[실시간 데이터 요약]` · `[선택한 분석 주제]`(+ 페르소나 · 지역 유형 · 리포트 모드).

## 왜

- **리포트가 1.8KB다.** 통째로 넣어도 1,700토큰이고, 검색해서 조각을 고를 이유가 없다. RAG는 여기서 정확도를 못 높이고 실패 지점만 늘린다.
- **화면 상태는 매 요청 달라진다.** 파인튜닝으로는 "지금 사용자가 보고 있는 것"을 담을 수 없다.
- 근거가 프롬프트에 그대로 있으니 **답이 왜 그렇게 나왔는지 추적된다.** 파인튜닝된 가중치는 못 따진다.

## 대신 잃은 것

- **입력 토큰이 매 요청 고정으로 나간다.** 요청당 약 1,700토큰.
- 리포트가 커지면 그대로 비용이 된다. → B5(RAG)를 남겨 뒀다.

## 비용을 줄인 방법

리포트를 잘라 넣는 대신 **블록 순서를 바꿨다.** 고정(역할·리포트·규칙)을 전부 앞, 가변(요약·주제·페르소나)을 전부 뒤로. OpenAI 자동 캐싱은 앞에서부터 같은 구간만 1,024토큰 이상일 때 재사용하는데, 가변 블록이 3번째 줄에 있어 **프리픽스가 60자뿐이었다 — 임계에 닿은 적이 없어 캐싱이 늘 0이었다.** 재배치 후 2,432자(전체의 95%), 실측 `cached_tokens=1024`.

리포트를 주제별로 잘라 넣는 안은 버렸다. 사용자는 화면에 없는 주제도 묻고, 그때 "리포트에 없다"고 답하면 절약이 아니라 품질 저하다.

## 지키는 규칙

프롬프트에 들어가는 문구는 **전부 백엔드가 갖는다.** 프론트는 화이트리스트된 열쇠(`topic`·`mode`·`persona`·`regionType`)만 보낸다. 프론트가 임의 문자열을 넣게 두면 그대로 프롬프트 주입 표면이 된다.
